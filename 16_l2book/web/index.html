A limit order book & matching venue in C —
Isolates for the books, fibers for everything that blocks.

The piece of software at the heart of every exchange: it holds every buy and sell order and matches them, fairly and fast. l2book is a US-equities venue built on libxtc: each symbol's book is a single-writer Isolate on its own core, every session is a fiber. The engine uses integer-exact pricing (int64 ticks, never floats), is fully deterministic, allocates nothing after the book is created, and ships the order surface of intrepidkarthi/orderbook. The engine below is the real thing — the same book.c, compiled to WebAssembly, running in your browser.

What is this?

16_l2book is an example in libxtc-examples: a central limit order book (CLOB), a matching engine, and a venue around them — order entry over TCP, a binary market-data feed, and this web console over HTTP and SSE. It exists to show libxtc’s two concurrency models working together, each where it fits: stackless Isolates (xtc_tnt) for the books, and fibers (xtc_proc) for everything that blocks.

The engine (book.c, book.h) is pure C11 with no libc beyond mem*, so the same file builds into the venue and into a freestanding wasm32 module. It’s not a hosted service or a production exchange — no accounts, custody, settlement, durability or authentication (the honest list is below). Everything you see on this page is powered by that exact engine.

First, what is an order book?

If you’ve never seen one, here it is from the ground up.

  1. People post offers. A bid is a buy order (“I’ll buy 5 at 100”). An ask is a sell order (“I’ll sell 3 at 101”).
  2. They’re sorted by price. Best bid (highest a buyer will pay) and best ask (lowest a seller will accept) sit in the middle. The gap between them is the spread.
  3. Size at each price is depth. Lots of size = a deep, liquid market that’s hard to move. Little size = thin, and prices swing.
  4. That whole ladder is the order book — a live list of everyone’s intentions, updating constantly. →

How matching works

When a new order can trade, the engine matches it by price–time priority: best price first, and among equal prices, first-come-first-served. Walk through it — each step runs on the real engine.

Press Start to build a book, rest an order, and send a market order that matches.

  • Maker — a limit order that rests and provides liquidity.
  • Taker — a market/crossing order that removes it, paying the spread.
  • Trades print at the maker’s price. Big orders “walk the book” and pay more (slippage).

Everything it does

The order surface of intrepidkarthi/orderbook, in C — all in the engine (book.h).

Order types

  • Market & Limit
  • Stop & Stop-limit
  • Trailing stop
  • Iceberg (the refill goes to the back of the queue)
  • Post-only (rejected if it would trade on entry)
  • Pegged (to bid / ask / mid + offset, priced at entry)
  • OCO (one-cancels-other)

Matching & priority

  • Price–time priority (FIFO)
  • Pro-rata allocation at a level
  • Trades at the maker price
  • Self-trade prevention (5 modes)
  • Time-in-force: GTC · IOC · FOK · DAY · GTD
  • Uniform-price opening auction (max volume, min imbalance, nearest the reference)

Market integrity

  • Price-band circuit breaker (± basis points of a reference)
  • Sessions: pre-open, continuous, halted, cancel-only, closed
  • Cancel, reduce keeping priority, replace losing it
  • Cancel-all for an account; cancel-on-disconnect
  • Ownership: a session never names another account’s order
  • Console only: spoof and order-to-trade-ratio detectors (signals.c)

Market data

  • L2 level events (a price level’s new total)
  • Snapshot + deltas, gap-free sequence numbers
  • Trade tape with the aggressor side
  • Binary TCP feed and SSE for browsers
  • A book digest that two equal books share

Built to venue standards — and honest about the rest

Money is never a float

Prices are int64 ticks (cents) and quantities int64 shares — no floating point on the money path, no clock and no globals in the engine. The console’s signals are floats; the book they are computed from is not.

Deterministic & replayable

Every call is a command whose effects come back as events in a caller’s buffer. The same command stream produces the same events and the same digest, byte for byte, on every platform — the console’s digest is the native build’s, and its seed replays the market of intrepidkarthi’s console print for print.

Fast, with real numbers

On their cross-engine tape (50,000 commands) all five engines produce the same digest; median replay: l2book 2.76 ms, CppTrader 4.26, geseq 5.93, intrepidkarthi 9.60, OrderBook-rs 54.9. On their latency scenarios, ported operation for operation, l2book’s medians are 1.9–4.4× lower and its p99.99 stays below 0.75 µs; theirs reaches 28–114 µs wherever an operation allocates. COMPARISON.md

End to end, over TCP

One closed-loop client, loopback TCP, order + acknowledgement: l2book p50 17.4 µs, 55k round trips/s (a plain loopback echo costs about 13 µs of that). Their gateway as shipped is 2.1 ms, because it polls each session’s outbound stream every 2 ms; with that poll set to 20 µs it is 74 µs. With sessions on an xtc_exec (--fiber-loops), 8 shards and 16 clients: 1/2/4/8 loops give 54k/149k/313k/383k round trips/s on the 48-core development host.

Tested hard

test_book: unit cases, two differential tests of 200,000 random commands against a naive reference matcher that shares no code (one near the touch, one over ±20,000 ticks), and a determinism check, clean under ASan and UBSan; planted bugs (LIFO within a level, an iceberg refill keeping its place, stops on the wrong side, a re-base that skips a bitmap word) each fail it. test_signals checks the console against intrepidkarthi’s own test vectors and their console’s output. l2book --self-test drives every shard over TCP; smoke.sh checks the compose box.

How it handles things

Each side is a dense window of 4,096 price levels under a two-level bitmap: best bid and ask, and the next level, are a find-first-set each. The window follows the book (a re-base), and levels outside it wait in a sorted overflow store, so any positive price rests. Orders live in a fixed pool indexed by uint32, FIFO per level; an open-addressed id map gives O(1) cancel. One writer per book, no locks: cross-core traffic is one SPSC ring per (sender, shard), and a shard busy-polls (--spin-us) before it parks.

What it does not have

No WAL and no durability: a restart loses every book. No authentication (a login names an account), no resumable sessions, no rate limit, no pre-trade risk caps. The venue table compares two programs that do different amounts of work; durability is not measured, and with a WAL that fsyncs every command both venues would be bound by the disk. Run it

A running market in one command, from a libxtc checkout:

docker compose -f examples/16_l2book/compose.yaml up --build
open http://127.0.0.1:8080/

The venue with its built-in market maker and noise flow, plus an outside flow client trading through the real order-entry port. The console at /console.html attaches to the live books (LIVE mode); smoke.sh checks the box end to end.

Or build it:

cd examples/16_l2book
make XTC_BUILD=../../build_unix check   # engine + console tests, venue self-test
make bench                              # the bare engine, one pinned core
./l2book --flow                         # venue + flow; console on :8080
./l2book --bench 20000                  # loopback round-trip latency
make wasm WASM_CC=clang                 # web/book.wasm for the console

The engine on its own: rest a sell, cross it with a buy.

book_config_t cfg = { .max_orders = 1u << 16, .tick = 1,
    .ref_price = 10000 };                 /* $100.00 in cents */
void *mem = aligned_alloc(64, book_bytes(&cfg));
book_t *b;
book_init(&b, mem, book_bytes(&cfg), &cfg);

book_event_t ev[64];
book_out_t out = { ev, 64, 0, 0 };
book_order_t ask = { .id = 1, .account = 1, .side = BOOK_SELL,
    .type = BOOK_LIMIT, .price = 10100, .qty = 5 };
book_submit(b, &ask, 0, &out);
book_order_t bid = { .id = 2, .account = 2, .side = BOOK_BUY,
    .type = BOOK_LIMIT, .tif = BOOK_IOC, .price = 10100, .qty = 3 };
book_submit(b, &bid, 0, &out);   /* BOOK_EV_TRADE: 3 @ 101.00 */
